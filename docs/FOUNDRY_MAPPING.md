# Mapping this project onto real Palantir Foundry

This repo reproduces the Foundry pattern (Datasets → Code Repository
transforms → Ontology → Workshop) as closely as possible **without** a live
Foundry workspace. Be precise about this distinction in interviews — it's a
stronger signal than implying you had Foundry access you didn't.

| Concept | In a real Foundry deployment | In this repo |
|---|---|---|
| Raw data ingestion | A Foundry **Dataset** created via a connector or file upload, with automatic schema inference and lineage tracking | `data/raw/raw_transactions.csv`, generated by `src/etl/generate_raw_data.py` |
| ETL transform | A `transforms.api.Transform` in a Foundry **Code Repository**, run on a Spark cluster, output written as a new versioned Dataset | `src/etl/pyspark_etl.py` (the real PySpark code, as you'd deploy it) — actually *executed* in this sandbox via the logic-identical `src/etl/pandas_etl.py`, since no Spark cluster is available here |
| Data quality | Dataset **Health Checks** / Expectations wired to the pipeline, visible in the Foundry UI | `src/data_quality/quality_checks.py` — same checks, run standalone and exported as JSON |
| Ontology | Defined in **Ontology Manager**: object types, properties, and link types backed by Foundry Datasets | `src/ontology/ontology_schema.py` (schema-as-code) + `src/ontology/ontology_export.py` (materializes real instances from the scored data) |
| Actions | Foundry **Action Types** — parameterized, validated write-back operations on Ontology objects | `src/ontology/ontology_schema.py`: `review_transaction`, `mark_alert_as_investigated`, `escalate_high_risk_transaction` — same state-transition logic, as plain Python functions instead of registered Action Types |
| Workshop | A **Workshop** application: drag-and-drop widgets bound directly to Ontology objects, with built-in auth, sharing, and write-back Actions | `dashboard/index.html` — a hand-built Workshop-style web console with the same four pages (Overview / High-Risk Transactions / Customer Investigation / Transaction Investigation), reading the ontology export as static JSON instead of a live Ontology binding |

## What genuinely carries over

- **The pipeline logic** (cleaning rules, data quality checks, feature
  engineering, model training/evaluation code) is real, runs, and would work
  unchanged (aside from I/O) inside a Foundry Code Repository transform.
- **The Ontology design** — which object types to model, which relationships
  matter, how Actions should be scoped — is the actual design work a Foundry
  builder does; only the deployment mechanism (Ontology Manager UI vs.
  Python dataclasses) differs.
- **The analytical thinking**: why ROC-AUC over accuracy for imbalanced
  fraud, why explainability matters to an analyst, how to structure an
  entity investigation — all directly transferable.

## What would need to change on real Foundry

1. `pyspark_etl.py` would be registered as a `@transform_df` (or
   `@transform`) function reading/writing Foundry Datasets by RID, not local
   Parquet files.
2. Data quality checks would be added as Dataset **Expectations**, which can
   block downstream builds on failure — this repo's `quality_checks.py`
   reports but doesn't gate the pipeline.
3. The ML training step would typically run in a Foundry **Code
   Workbook** or **Model** resource, with the trained model registered so it
   can be applied to new data via a **Model Ontology** binding.
4. The Ontology object types would be created in Ontology Manager, bound to
   the underlying Datasets, and the Actions registered as proper Action
   Types with validation rules and permission scoping.
5. The dashboard would be rebuilt in Workshop itself, binding widgets
   directly to live Ontology objects instead of a static JSON export — this
   gets you real-time updates and built-in write-back instead of a read-only
   console.

## Suggested learning order (from the original project brief)

1. Palantir Foundry fundamentals (Palantir Academy)
2. Datasets + ingestion
3. PySpark transformations
4. Data pipelines (Code Repositories)
5. Data quality + lineage (Expectations)
6. Ontology fundamentals
7. Object types + relationships (Ontology Manager)
8. Actions
9. Workshop
10. Rebuild this Fraud Risk project on real Foundry, end to end
11. Document it properly on GitHub
12. Add to resume — accurately

Palantir's own Academy and Foundry documentation are the right primary
sources for steps 1-9 rather than third-party tutorials.
